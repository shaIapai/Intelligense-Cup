# «Пульс» — ИИ-агент для ретрансляции обращений из поддержки в разработку

Решение кейса **«ИИ-агент для ретрансляции обращений в поддержку»** — Intelligence CUP от «Газпром нефти», 2026, направление «Искусственный интеллект».

## О чём решение

В компании десятки цифровых продуктов, а пожелания и повторяющиеся проблемы пользователей остаются в тикетах и редко доходят до продуктовых команд. «Пульс» раз в час забирает новые обращения (заявки, звонки, скриншоты), находит повторяющиеся темы и передаёт значимые из них продуктовым командам. Службе поддержки при этом ничего делать не нужно.

**Цепочка работы:**

```
обращение → карточка (продукт, модуль, тип, суть)
          → тема из реестра продукта
          → счёт уникальных клиентов по client_id
          → бэклог (комментарий со статистикой или черновик задачи)
          → недельный дайджест / оповещение при всплеске
          → проверка эффекта после релиза
```

**Ключевые решения:**

- **Гибрид кода и LLM.** Выгрузку, маскирование, статистику и пороги считает код. Qwen нужен только там, где требуется суждение: понять суть обращения и сопоставить с известными темами.
- **Реестр тем вместо эмбеддингов.** У каждого продукта свой реестр (до 40 активных тем) целиком помещается в промпт. Лишний сервис и векторная база не нужны.
- **Значимость по уникальным клиентам.** Повторные обращения одного клиента счёт не раздувают.
- **Четыре сервиса и одна БД.** Коннектор, подготовка (ASR/VL + маскирование ПДн), ядро агента, шлюз действий. Запись наружу идёт только через шлюз.
- **Только внутренний контур.** Qwen 3.8, Qwen-ASR и Qwen-VL; внешние API не используются.
- **Человек в контуре.** Задачи в трекере создаются только после подтверждения владельцем продукта.

## Результаты (базовый сценарий)

| Показатель | Значение |
|---|---|
| Нагрузка | ≈53 мин GPU в сутки, ≈15 мин в пиковый час |
| Снято обращений в год | ≈9,4 тыс. (5,9% потока) |
| Потолок инвестиций (окупаемость за 3 года) | ≈5,0 млн ₽ |
| Высвобождаемое время поддержки | ≈3,5 тыс. часов в год (≈1,8 ставки из 40) |

Расчёт ведётся по трём сценариям (консервативный, базовый, оптимистичный) с учётом макроусловий. Все допущения помечены и подлежат проверке на истории и пилоте.

## План внедрения

1. Разовый прогон по истории 2–3 пилотных продуктов (≈12 тыс. обращений, ≈22 ч GPU) — базовая линия метрик.
2. Теневой режим 2–4 недели: дайджесты видят только владельцы пилотных продуктов.
3. Пилот 6–8 недель: полный цикл с бэклогом и кнопками обратной связи.
4. Подключение остальных продуктов по одному с мини-приёмкой на 50 обращениях.

## Допущения

Около 40 продуктов (по одному менеджеру на продукт); 440–480 обращений в сутки; в тикете есть `client_id`; 30% звонков по 4 минуты; скриншот у 25% заявок. Полный список и способы проверки — в основном документе.
